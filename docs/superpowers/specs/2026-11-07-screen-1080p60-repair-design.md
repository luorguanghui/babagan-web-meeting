# 整屏 1080p60 修复设计

用户要求保持 1080p、持续真实 60fps，并减少快速变化时的明显压缩色块，拒绝以 360p 或重复帧计数达标。用户已同意按网络能力提高码率，并明确接受本机原生采集组件。后续测试只允许测试标签页及合成画面，真实桌面采集不得继续测试。

线上基线 70158d9 的网页源码与发布 fcbfcade 相同。Edge 156 原生 WGC 供帧约 53–56fps，切换 GPU 纹理没有达到真实 60fps。强制 min90 只能提高包含重复画面的统计值，已排除该方案并撤回实验代码。NVIDIA H.264 的 Media Foundation 软件码率控制可在输入正常、没有网络丢包时内部丢帧；禁用相应性能特性的独立浏览器对照，编码器内部丢帧归零。静止到复杂运动还存在码率探测默认最大值约 5Mbps 与 RTP 上限 20Mbps 不一致的问题。

## 方案

增加可选择使用的 Windows 原生组件，使用已安装 FFmpeg 的 DXGI 捕获，保留现有网页、会议音频及 P2P、TURN、Cloudflare SFU 传输。组件只支持一个活动显示器，不能确认来源时拒绝原生捕获；网页仍提供普通浏览器采集选项。

浏览器先提供明确的屏幕／声音选择器，仅在确认主屏后打开原生视频。原浏览器视频作为未发布的低帧率权限哨兵保留，浏览器“停止共享”会终止原生采集。停止、离会、撤销、异常及未完成的启动均可取消；晚到的授权／轨道会释放，重新共享等待旧授权清理。

本机服务只绑定 127.0.0.1 随机端口，每次启动生成随机能力令牌，严格校验 Origin。启动信息从 URL fragment 进入 sessionStorage 后立即从地址栏移除。生产通道使用带 Bearer 认证的 HTTP 流和 BYOB 读取，避免 Edge 原始 WebSocket 大消息吞吐瓶颈。协议为长度受限的格式 JSON，然后固定头部与 I420 数据；背压最多保留两帧。

DXGI 采集请求两倍目标节奏，按真实采集时间选择至多每目标间隔一帧，明确关闭 `dup_frames`，不使用 CFR/fps 滤镜补帧；另记 contentChangedFrames 区分采样与像素变化。真正静止时可能没有新采集帧，浏览器仅以最多 1Hz 发送单独标记的旧画面保活，避免首帧丢在连接建立之前、P2P 误报停滞和 SFU 30 秒媒体过期。refreshFrames 与真实 receivedFrames/submittedFrames 分开统计，保活不算运动 60fps 的证据。

浏览器将 generator writable 交给独立线程，用约 40ms 缓冲和精确计时平滑到达抖动。跨线程待确认传输最多四帧，线程内最多四帧排队加一帧写入；额外保留一份保活快照和最多一个保活写入。过载时丢弃过期原帧，真实采集时间戳保持不变。静止恢复后的真实桌面画质和帧率仍需验证，不能从合成源恒定采样自动推断。

原生模式默认动态 60fps、自动编码。自动编码仅在能力查询确认硬件支持时优先 AV1，保留硬件 H.264 回退；显式 H.264、VP8 和普通浏览器入口保持原语义。动态内容提示 motion 与保分辨率策略独立。原生协商对视频同步 x-google-start-bitrate 和 x-google-max-bitrate 为实际每路上限，不设置最低码率，拥塞控制继续负责实际速率。

动态和细节 60fps 档未被用户手动覆盖时建议最高 20Mbps；P2P 三人及以上建议 10Mbps，原 40Mbps 总预算保留。Cloudflare SFU 单路发布按一个上行计算。显式手动选择继续受尊重，拥塞控制继续负责实际发送速率，不强设最低码率。

启动器使用独立 Edge 配置，启用经过测试的硬件 AV1，关闭已定位的 H.264 软件码率控制性能特性，避免后台计时器降频。它不关闭安全防护、不自动批准权限、不开放调试端口、不修改默认浏览器。首次按浏览器提示允许本机网络访问。CLI 启动前验证 FFmpeg／Edge，状态回报不含令牌，启动器只在就绪后报告成功。

## 验证

协议、尺寸、认证、取消、授权清理、来源选择、参数传播、背压和限帧均有回归测试。正式性能夹具使用真实生产模块，仅把原生输入替换为合成 FFmpeg 图像，实际运行本机传输、Edge 编解码和 RTP；另设静态与运动切换和后台标签页阶段。记录帧率差分、分辨率、QP、码率、发送排队时间、丢包及实际解码画面变化。

这些测试不替代用户两台电脑之间的端到端验收，也不能证明所有网络或显卡都稳定 60fps。若源、编码或网络仍达不到目标，结果需明确保留，而非降低验收阈值。当前用户限制下，完整真实桌面路径的最终验收保持待测。
