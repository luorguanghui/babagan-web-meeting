# 项目自带 WASM 屏幕编码与 P2P 数据传输设计

日期：2026-10-10（Asia/Hong_Kong）。源码基线：`363cf8984d120ed0bcf2e53c78e97a9b665cc3ba`。

## 1. 已确认的用户要求

- 使用项目内的 WebAssembly 软件视频编码器，绕开浏览器 WebRTC 视频编码器的丢帧策略。
- 必须同时支持 H.264 和 VP8，默认 H.264。
- 在现有网页会议中工作，不要求共享者安装本地 EXE。
- 改造发送端和接收端；继续使用现有 P2P/TURN 能力及授权、房间、共享锁。
- 目标是改善真实高动态画面的 1080p60 表现，不能通过重复帧、伪造帧率或隐藏丢帧实现表面达标。

以下是针对现有功能的设计选择：保留电脑声音共享、共享音量、独立麦克风语音、停止／撤销／重连以及观看者明确选择 SFU。CPU／网络跟不上时显示实际吞吐和项目处理原因，禁止无界积压。

## 2. 当前实现与必须改变的边界

目前 `P2pShareController` 将原始屏幕轨道交给 `RTCPeerConnection.addTransceiver`，浏览器进行视频编码；观看者从 `ontrack` 获取浏览器生成的远端媒体轨道。

新方案中 P2P 屏幕视频没有视频 RTP sender：原始帧进入项目编码 Worker，输出编码帧经 `RTCDataChannel` 传输。浏览器仍提供屏幕采集、ICE/DTLS/SCTP、接收端解码和最终显示，这些环节不等于浏览器视频编码器。

不得将 WASM 编码结果解码成原始轨道，再交回原有视频 transceiver，否则会产生第二次浏览器编码。

## 3. 编码器与可复现构建

### H.264：默认

选用 Cisco OpenH264 `v2.6.0`，固定源码提交 `652bdb7719f30b52b08e506645a7322ff1b2cc6f`，通过项目的 C/C++ 薄封装编译为 Emscripten WASM。

- 提供逐帧 I420 输入及 Annex B H.264 输出，不建立 MP4 文件、不积累整场会议的文件数据。
- 明确设置 `bEnableFrameSkip=false`；输出为空或 SDK 返回 skip 必须计入真实编码统计，不能视作已编码成功。
- 使用实时、低复杂度、单空间层、单时间层、无 B 帧配置；请求关键帧及更新目标码率由项目控制。
- 支持线程构建及单线程构建；线程数限制为 1–4，不创建每名观看者一个编码器。
- 默认关键帧周期 2 秒，接收端恢复或观看者新加入时可请求新关键帧。
- 解码 codec 字符串由实际 SPS 的 profile、constraint 和 level 字节生成，不假定某一设备的 H.264 profile。

### VP8：可选

选用 `@libav.js/variant-vp8-opus@6.10.9`，通过 libvpx 的逐帧编码 API 使用实时配置，关闭编码器基于码率的自动跳帧，禁用 lookahead，提供与 H.264 相同的编码适配接口。

H.264 与 VP8 的编码适配层都不得调用浏览器 `VideoEncoder`，也不得用浏览器 `MediaRecorder` 产生发送视频。`auto` 编码选项仅在两种项目软件 codec 之间选择，优先 H.264。

WASM、Worker、类型定义和对应许可证／源代码清单均由项目构建发布并从本网站同源加载。生产运行不从 CDN 临时下载二进制或执行第三方脚本。构建器版本和最终二进制 SHA-256 在实现时随构建清单固定；没有通过逐帧基准的二进制不能进入应用集成。

## 4. 采集与编码生命周期

沿用 `getDisplayMedia` 及当前系统音频回音隔离选择。保留质量档位与源宽高比：分辨率优先／标准 1080p30，动态 1080p60；不放大低于 1080p 的源。

`MediaStreamTrackProcessor` 的实际帧是输入依据。转换为偶数尺寸 I420 后传给专用编码 Worker；浏览器只支持 RGBA 输出时使用项目转换层，不阻塞 React 主线程。

编码流水线：捕获 → 原始帧转换 → 软件编码 → 分发给观看者。一个共享源仅编码一次，编码包按观看者连接分发；新加入观看者等待配置及关键帧。

编码统计分别计量：捕获帧、读到的原始帧、提交编码帧、实际产出帧、编码耗时、队列年龄。不能用 `getSettings().frameRate` 冒充实际捕获帧率。

编码任务不无界堆积：原始帧队列最多 6 帧，待处理帧年龄上限 150 ms。资源不足时由项目明确丢弃过期帧并计数；正常负载下不得按低码率估计提前丢弃健康输入。被丢弃／消费的所有 `VideoFrame` 必须关闭，停止后释放 Worker、WASM 编码器、读取器和原始帧。

这些上限控制失败时的延迟和内存，不构成所有用户设备都能 60 fps 的保证；先测真实软件编码吞吐，再解释剩余限制。

## 5. P2P 数据通道与协议

复用现有 meeting P2P 信令、offer/answer/ICE generation、TURN provider 和授权。新旧媒体实现的选择由显式协商决定，不将数据通道的开启当成首帧成功。

每个观看者有两条通道：

- `meeting-screen-control-v1`：可靠、有序；承载协议版本、能力、codec 配置、共享 generation、关键帧请求、解码错误及接收反馈。
- `meeting-screen-media-v1`：无序、`maxRetransmits=0`；承载分片后的编码视频和共享音频。

媒体分片最大 12 KiB，包含协议版本、共享 generation、媒体种类、帧序号、微秒时间戳、关键帧标记、分片索引／数量和总长度。单视频帧上限 2 MiB，分片数量上限 256；畸形字段、重复片、过期 generation、乱序／不完整帧均在解析边界处理。

发送端按实际 `pc.sctp.maxMessageSize` 限制最终消息尺寸。单观看者通道缓冲上限 256 KiB，发送等待上限 150 ms；过慢观看者单独停止接收该帧，不阻塞其他观看者。丢掉参考帧后等待／请求新关键帧，不能把破损 GOP 继续展示成健康画面。

接收端未完成组装的帧最多 8 个、总占用不超过 8 MiB，组装期限 150 ms。丢失片、解码错误或过期参考链触发关键帧请求；请求间隔至少 500 ms，防止关键帧风暴。

码率档位沿用 5／8／10 Mbps 与 40 Mbps 总上行预算。预算计算包含共享音频和传输余量；编码目标由当前有效观看者预算决定，不能因为静态画面实际码率低而自锁到更低编码上限。RTC 拥塞控制仍作用于数据通道网络，不属于浏览器视频编码。

## 6. 共享声音与播放时钟

麦克风语音继续使用 LiveKit，不参与本次屏幕视频编码替换。

电脑声音属于屏幕媒体时钟。通过 AudioWorklet 读取共享音轨，输出 48 kHz 立体声 PCM，在独立音频 Worker 中通过 libav.js/libopus 编码 Opus，20 ms 包、128 kbps 目标。音频采用同一共享 generation 和微秒时间戳；不另建无时间关联的音频 RTP 流来假装已解决音画同步。

接收端使用 AudioDecoder／AudioWorklet 播放共享声音，支持原有接收音量；视频以同一播放时钟调度。初始缓冲目标 100 ms，最大 200 ms；时间戳回退、声轨缺失、音频自动播放被阻止、输入停止和长时间漂移都有独立处理及测试。

音视频同步验收采用已知时间标记的运动画面与音频脉冲，测量持续播放及重连后的偏差；不能仅凭同一连接或同一时间戳字段声称已同步。

## 7. 解码、显示与界面

接收视频使用浏览器 `VideoDecoder`，分别验证 H.264 和 VP8 的真实配置支持；软件编码不要求接收端也使用软件解码。

解码帧送入播放适配层：支持时使用 VideoTrackGenerator／MediaStreamTrackGenerator，只作为本地 `<video>` 的原始帧显示源；兼容路径用 canvas 直接绘制。生成的轨道不得发送回任何视频 RTP sender。

`ScreenStage` 接收统一显示源接口，保持现有宽高比、全屏、共享者名称、系统音量及首帧交接。编码器名称明确显示“项目 WASM / OpenH264”或“项目 WASM / libvpx”，指标来自实际项目计数，不能拿不存在的视频 RTP 统计填充它。

新增编码方式选择：项目软件编码（默认）／浏览器原生编码（显式兼容选项）；codec 默认 H.264，可选 VP8。能力不满足或 WASM 初始化失败时明确说明，并保留语音会议；不静默回到浏览器视频编码。

旧客户端没有数据通道媒体协议支持时，显示需要刷新或明确选择兼容模式。手机继续作为观看／语音端，能力检测失败时可以显式选择原有 SFU 模式。

## 8. SFU 与恢复行为

P2P/TURN 默认使用项目编码数据通道。仅在观看者明确选择 SFU 时沿用 LiveKit 原始轨道发布；该路径仍由浏览器编码，并在界面和统计中明确表示，不能标为 WASM 编码。

保留目前的路径偏好、ICE 凭据刷新、P2P 重试和共享锁清理。每次新 offer generation 关闭旧通道、丢弃旧组装状态并发送新 decoder 配置／关键帧。故障不得自动创建常驻 SFU 屏幕副本。

## 9. 线程、部署与资源边界

多线程 WASM 需要同源资源及 COOP/COEP。为应用页面和 Worker 资源配置正确隔离响应头，验证登录、现有 SDK/WSS、音频、源选择和移动观看行为。浏览器无法提供隔离／线程能力时使用显式可识别的单线程项目编码实现，不自动使用浏览器 VideoEncoder。

构建／部署增加 WASM 构建产物和版本化静态资源；更新器必须能验证 WASM 的 HTTP 状态、MIME、哈希及隔离头。处理源配置变化的媒体／Caddy 更新不能冒充现有仅更新 API/web 的部署。

服务端继续不编码、不解码、不保存会议媒体；TURN 只中继加密数据。协议解析限制、generation 隔离、帧／缓冲尺寸、Worker 关闭和恶意分片测试是发布必需检查。

## 10. 实施顺序与验收门槛

1. **编码可行性**：构建并核验 OpenH264 与 libvpx WASM 的逐帧接口，分别编码 1920×1080 的静态、平移纹理及复杂高动态场景，测量转换＋编码端到端吞吐、p50/p95 耗时、实际产出和内存。编码器内部 skip 必须关闭并实测。
2. **单观看者闭环**：真实 Worker → P2P 数据通道 → 解码 → 显示，同时证明没有调用 VideoEncoder／MediaRecorder，没有屏幕视频 RTP sender。
3. **声音与生命周期**：共享音频同步、停止／撤销、重复开始、断网、重连、超慢接收、协议损坏及资源清理。
4. **多人及部署**：4 名观看者、P2P 与两种 TURN、显式 SFU、线程隔离响应头、移动端能力退化；维护代码、测试、构建、更新和回滚文档。

60 fps 档在测试机器上的完整流水线必须能够持续处理真实 60 fps 输入：180 秒高动态测试中实际编码／解码平均至少 57 fps，完整视频帧的第 95 百分位端到端延迟不超过 250 ms；不能用丢掉大部分输入或重复画面达标。30 fps 档平均至少 28.5 fps。没有达到这些门槛时保留实际结果，不切换生产默认。

声音开启时持续 10 分钟的音视频偏差目标不超过 80 ms；5 次重连后恢复正确 generation、配置与关键帧。30 分钟运行不得出现原始帧或编码队列无界增长。

如果编码可行性阶段测得默认 H.264 软件编码无法持续达到 60 fps，应先报告实际机器结果和限制，不能直接部署一个仅改名的软件编码模式或删除 H.264 要求。

## 11. 验证过的技术依据

- [OpenH264 源码](https://github.com/cisco/openh264/tree/v2.6.0)：编码参数提供明确的 frame-skip 控制、实时配置及逐帧码流输出。
- [libav.js API](https://github.com/Yahweasel/libav.js/blob/master/docs/API.md)：提供逐帧编码接口，VP8／Opus 变体可用；H.264 变体没有可直接核验的已发布 npm 包，需要独立构建。
- [Emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html)：部署线程构建需要 COOP/COEP 与 SharedArrayBuffer。
- [媒体轨道处理](https://www.w3.org/TR/mediacapture-transform/)和 [WebCodecs](https://www.w3.org/TR/webcodecs/)：接收端解码／本地显示可使用浏览器，发送端项目视频编码与之区分。
