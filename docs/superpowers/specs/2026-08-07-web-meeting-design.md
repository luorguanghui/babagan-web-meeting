# 网页会议系统总体设计

日期：2026-08-07

## 背景

现有基础设施是一台位于阿里云武汉地域的 Debian 12.10 轻量应用服务器，规格为 2 核、2 GiB、40 GiB 和 200 Mbps 峰值公网带宽，无固定月流量额度。域名 `babagan.cloud` 已托管到 Cloudflare，并已配置 `meet`、`rtc`、`turn` 三个子域名。

产品只服务单个 4–5 人会议，核心能力是实时语音以及一名成员的高质量屏幕和电脑声音共享，不需要摄像头、录制或其他协作功能。

## 已评估方案

### 方案 A：LiveKit SFU

优点是 Web SDK、屏幕音频、权限、网络自适应、断线重连和 TURN 能力成熟；服务端不转码时适合当前服务器。缺点是需要正确配置公网 IP、UDP、防火墙和证书。

### 方案 B：mediasoup + coturn

控制粒度最高，但房间信令、权限、恢复和媒体状态均需自行实现，工程与测试成本较高。

### 方案 C：浏览器 P2P

服务端最轻，但屏幕共享者需要向每名观看者分别上传，4 名观看者会显著提高共享者上行压力，且复杂网络可靠性较差。

## 结论

采用方案 A：React + TypeScript、Fastify、SQLite、LiveKit、Caddy 和 Docker Compose。LiveKit 只进行 SFU 转发，不进行录制、合成或转码。

## 架构设计

- `meet.babagan.cloud` 通过 Cloudflare 橙云访问 Caddy，提供网页和 API。
- `rtc.babagan.cloud` 以 DNS only 直连 Caddy，再通过 WSS 到 LiveKit。
- WebRTC 媒体优先直连 LiveKit UDP 端口。
- `turn.babagan.cloud` 提供 TURN/UDP 443，RTC/TCP 7881 作为进一步回退。
- Fastify 负责会议生命周期、权限、主持人会话及 LiveKit Token。
- SQLite 仅保存短期会议元数据和哈希后的凭据。

## 权限设计

- 固定管理密码建立主持人会话。
- 主持人可创建/结束会议、移除成员、授予或撤销共享权限。
- 所有成员默认静音加入，之后均可自由开麦。
- Token 禁止摄像头和数据轨道；普通成员只允许发布麦克风。
- 获授权成员通过 LiveKit 权限更新获得屏幕及屏幕音频发布能力。

## 质量设计

- 默认 1080p/30fps，高动态模式 1080p/60fps。
- 弱网时保持语音优先，屏幕轨道自适应降码率或分辨率。
- 目标为正常网络下语音端到端延迟低于 300ms，5 秒内入会。
- 5 人、单路 1080p60 时 CPU 持续低于 80%，内存不超过 1.8 GiB。

## 安全与隐私

- HTTPS/WSS、DTLS-SRTP、短期 Token、Argon2id 哈希、严格 Cookie 和接口速率限制。
- 不记录明文密码、Token、Cookie 或媒体内容。
- 不保存音频、屏幕帧或真实身份资料。
- 首版不承诺端到端加密；服务器作为 SFU 可以访问传输中的媒体包。

## 运行边界

- 一个活动会议，最多 5 人。
- 创建后 24 小时失效；空房 10 分钟回收；断线身份保留 30 秒。
- Windows 10/11 Chrome 与 Edge 为唯一正式验收桌面环境。
