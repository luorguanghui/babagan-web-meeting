# WASM 发送节奏与接收统计调查

日期：2026-10-10。

## 现象与证据

Android 接收端截图显示编码 2511 帧、解码 1162 帧、显示 1161 帧、项目丢帧 0、编码耗时 11.61ms。已解码帧几乎全部显示，区别于此前显示队列饥饿问题；缺失发生在显示之前，但单张截图不能区分发送拒绝、网络组帧或解码等待。

实际 Edge 共享端运行线上 e6b77df，软件 H.264、1920×1080、60fps 配置、每位观看者预算 8Mbps。活动观看者对应的编码帧数 7671、采集 7672、采集队列丢帧 0，但发送器累计拒绝 508 帧。另一已关闭会话累计编码 2735 帧、发送拒绝约 223 帧。控制通道的 stats 原来只传采集队列丢帧，没有包含发送器损失，解释了接收面板可能仍显示 0。

当前静态场景的 20 秒诊断观看者采样：完整接收 650 帧、解码增加 650、显示增加 650；组帧损失和关键帧请求均为 0。临时动态图层的 16 秒采样也未重现发送拒绝。不能将这个正常样本当作手机卡顿已解决，也不能断言全部缺失来自发送器。

## 已复现的代码缺陷

ChannelSender 在每个分片发出后执行 `nextSendAt = max(nextSendAt, now) + 分片耗时`。定时器比约定时间晚唤醒时，多出的等待反复被加入下一片期限，调度抖动逐渐降低实际吞吐。与编码性能、物理网络剩余带宽不同，这是项目自己的限速逻辑造成的损失。出现发送拒绝后，发送端暂停普通帧直到新的关键帧，接收端在序号缺口后也等待恢复；这会进一步放大停顿。

确定性复现：每帧 13750 字节、60fps，加帧头和 12% 开销约 7.426Mbps，低于 8Mbps；模拟定时器最少 8ms 唤醒，600 帧发送花费约 14.39 秒，达不到原本约 10 秒的输入速度。

修复保留原来的发送期限，允许补回有限的晚唤醒额度，额度最多为一个 12KiB 消息的发送时间，瞬时发送突发仍受界限约束。150ms 等待、256KiB 缓冲上限、队列上限、码率预算及媒体通道可靠性选项不变。接收端收到的 stats 在现有“队列／传输丢帧”汇总中包含发送拒绝，未改变控制消息格式。

## 验证

- 新增 8/16ms 唤醒抖动、长时间空闲后突发上限及远端发送丢帧统计回归；抖动与统计测试有旧实现失败证据，修复后通过。
- 全量 60 个测试文件、904 个测试通过；lint、生产构建通过；独立代码审查无 Critical/Important 问题。
- 真实 Edge 创建本机 P2P 数据通道并经生产 ChannelSender/FrameAssembler 发送同样的 360 帧，8Mbps 预算，发送 sleep 最少 8ms，供帧 60fps：

| 指标 | 原实现 | 修复后 |
| --- | ---: | ---: |
| 输入帧 | 360 | 360 |
| 发出且完整接收帧 | 230 | 360 |
| 发送器拒绝 | 130 | 0 |
| 接收组帧损失 | 0 | 0 |
| 测试时长（含末尾250ms收尾） | 6.32s | 6.23s |

此测试隔离传输节奏，负载是合成字节，不包含视频编码或解码，也不是手机网络丢包测试。它确认发送器缺陷和修复，不能据此宣称已解决 Android 卡顿的所有原因或保证 1080p 60fps。手机刷新并重新共享后仍需复测；媒体通道当前仍无重传，实际丢包和解码恢复损失需要另行测量。
