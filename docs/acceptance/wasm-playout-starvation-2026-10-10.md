# WASM 接收端播放队列修复验收

日期：2026-10-10。

用户提供的接收端统计显示：编码 30903 帧、解码 22933 帧、显示 8925 帧，项目丢帧 14005。解码和显示之间的差额接近项目丢帧计数，说明需要检查接收端播放，而不能仅凭共享者预览正常判断远端播放正常。

## 原因与修复

接收端 PlaybackClock 使用初始 100ms 播放缓冲，而解码后显示队列最多只有 6 帧。在 60fps 下，如果解码回调先于播放定时器执行，新帧会把刚要到显示时间的最旧帧淘汰。持续输入可以导致第一帧始终无法显示，onStream 不触发；新观看者因此也可能显示没有屏幕共享。

将显示队列上限调整为 12 帧，覆盖现有最多 200ms 的视频缓冲；仍保留队列上限和过期丢帧，所有帧继续显式关闭。最坏情况下队列帧内存上限相应增加。另将 canvas 尺寸赋值改为仅在分辨率变化时执行，避免每帧重置画布。

编码器、码率预算、每位观看者独立编码和媒体协议均未调整。

## 验证

- 回归测试经实际 VideoDecoder 输出回调、PlaybackClock、显示队列和播放 tick 执行。旧实现持续 60fps 输入时 onStream 调用为 0；修复后 30/53/60fps 各 90 帧均触发首帧，无播放队列丢帧，且关闭后所有帧恰好释放一次。
- 全量测试：59 个文件、894 个测试通过；lint 与生产构建通过；独立代码审查无阻塞项。
- 实际 Edge 浏览器运行 OpenH264 worker → P2P 数据通道 → VideoDecoder → canvas 流，640×360、请求 60fps、传输预算 8Mbps、12 秒，同场景原实现与修复实现对比：

| 指标 | 原实现 | 修复后 |
| --- | ---: | ---: |
| 编码帧率 | 44.85 | 44.19 |
| 解码帧数 | 537 | 528 |
| 显示帧数 | 365 | 523 |
| 显示帧率 | 30.37 | 43.52 |
| 接收端丢帧 | 167 | 0 |

编码吞吐相近，接收端显示损失明显下降。此对比验证播放修复，不代表所有 1080p 设备或手机均达到 60fps；用户真实设备的持续播放仍需部署后复测。用户 Edge 页面上的诊断探针及临时动态图层已移除，诊断成员已离会。
