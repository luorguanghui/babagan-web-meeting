# 纯视频共享移除固定播放延迟

日期：2026-10-10。

用户确认未共享电脑声音；30fps 流畅，1080p60fps 卡顿。接收端截图显示编码 57fps、耗时 9.12ms、编码 1357 帧、解码 894 帧、显示 90 帧、队列／传输丢帧 798。此次大量损失发生在解码后，不能仅归因于发送或解码器吞吐。

## 原因与行为变化

原 PlaybackClock 在首个音频／视频帧时锚定一次，设置 100ms 初始播放缓冲；纯视频也必须经过这个时钟和定时显示队列。后续接收／解码延迟如果持续增加，帧会相对原锚点一直超出 200ms 过期阈值。代码不断丢弃已解码帧，时钟却没有恢复机制，形成“仍在解码但画面停止”的状态。

纯视频没有共享声音时间轴需要同步。现在根据协议 config.audio 明确选择播放方式：audio=false 时解码输出立即绘制 canvas 并 requestFrame，不再经过固定100ms时钟、延迟显示FIFO或其过期规则。audio=true 继续使用原共同时钟与有界显示队列。保留代际／解码器身份检查、分辨率限制、canvas尺寸变化检查；提交显示后在finally关闭VideoFrame。

这并不消除编码、网络、组帧、解码和浏览器合成自身耗时。码率预算、编码器及传输可靠性设置不变。共享声音路径的持续延迟恢复未在本次改动范围内。

## 验证

- 30/60fps 持续输入180帧，90帧后将到达时间整体推迟450ms。真实VideoDecoder输出回调到播放tick的回归，在旧实现60fps下仅显示84帧；新实现180帧全部提交显示，无播放丢帧，所有帧恰好关闭一次。
- 首个纯视频解码帧立即触发onStream/requestFrame，不等待100ms或tick。该测试旧实现失败、新实现通过。
- 保留audio=true的30/53/60fps队列回归，并验证配置有共享声音时首帧仍等待100ms且附带音轨。
- 全量60个文件、908个测试通过，lint与生产构建通过，独立代码审查无阻塞问题。
- 真实Edge 1920×1080、H.264 Worker→P2P→VideoDecoder→canvas流，60fps配置、8Mbps传输预算，10秒测试；前2秒正常，后续所有媒体消息额外延迟450ms。结果：

| 指标 | 原实现 | 修复后 |
| --- | ---: | ---: |
| 最终采样解码帧 | 242 | 250 |
| 最终采样提交显示帧 | 47 | 250 |
| 播放阶段丢帧 | 195 | 0 |
| requestVideoFrameCallback 实际呈现回调 | 47 | 251 |
| 最后实际呈现相对测试开始 | 2.137s | 10.028s |
| 测试总时长 | 10.080s | 10.052s |

修复后关闭流程期间还有一次浏览器呈现，故回调计数略高于关闭前统计快照。证据说明原实现的永久显示停顿消失、新实现在延迟下持续呈现；不代表测试达到了60fps，也不是实际Android网络和硬件的验收。该canvas来源测试仍有采集／编码吞吐限制，手机需部署后复测。
