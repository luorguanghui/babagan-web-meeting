# Edge 原生共享修复与验收记录

用户要求在 1080p 下稳定共享真实 60fps，快速变化时减少明显色块，不能以降到 360p 达标。用户同意提高可用码率并增加本机采集组件。用户随后限定测试只使用测试标签页；该限制后所有性能测试均使用合成图像，未继续采集桌面。

本次交付是本地修复候选版。合成链路已接近目标，但真实 DXGI 整屏、跨网观看和完全静止后恢复的最终验收仍待进行，不能宣称所有原始问题已经彻底解决。线上网页仍为 `/assets/index-B36QEf01.js`，健康检查为 ready；本轮尚未发布。

## 已定位的原因

| 环节 | 证据 | 修复 |
| --- | --- | --- |
| Edge WGC 整屏采集 | 原生日志及编码前帧号测量约 53–56fps；强制 min90 的 60fps 统计包含重复内容，GPU 纹理对照也未达标 | 新增 DXGI 本机采集入口，浏览器原有采集仍可选择；撤回 min90 实验 |
| H.264 编码侧控制 | 稳定生成帧输入下，NVIDIA Media Foundation 编码器内部丢帧 346，队列丢帧 9；禁用相关软件码率控制后内部丢帧 0 | 专用 Edge 配置关闭该性能特性；原生自动编码优先实际硬件支持的 AV1，保留 H.264 回退 |
| 初始带宽探测 | 仅设置 RTP 20Mbps 上限，日志中探测仍被约 5Mbps 默认值限制；静止转运动时目标回落、排队增长 | 原生路径的 offer/answer 同步实际每路的 startup/max bitrate 提示，无最低码率，保留拥塞控制和 40Mbps 总上行预算 |
| 本机原始帧传输 | Edge 仅接收 WebSocket 大帧约 40fps；相同数据经 HTTP BYOB 接近 60fps | 使用认证 HTTP 流，限制包尺寸及两帧背压，修复传输开销导致的第二帧误丢弃 |
| 帧到达与线程调度 | 浏览器接收／构造约 60fps，WebRTC 输入仍约 52fps；主线程在切换测试标签页后继续掉帧 | 独立线程持有 generator writable，40ms 时间戳缓冲与精确计时；修复累计调度偏移，保持原始帧时间戳 |
| 来源重复输出 | FFmpeg `ddagrab` 默认可重复上一帧；`fps_mode passthrough` 不会关闭该源级行为 | 明确使用 `dup_frames=0`，启动前验证运行时支持，旧 FFmpeg 6.0 会拒绝启动 |

浏览器内部机制可对照 [Chromium 桌面采集调度](https://raw.githubusercontent.com/chromium/chromium/main/content/browser/media/capture/desktop_capture_device.cc)、[WebRTC 输入按到达时间适配](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/platform/peerconnection/webrtc_video_track_source.cc)及 [FFmpeg ddagrab](https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/vsrc_ddagrab.c)。源码说明机制，本机日志与对照实验才是此次归因依据；不能把上游主分支当作当前 Edge 二进制的逐行证明。

## 正式合成链路测试

2026-11-07，Edge 156.0.4314.58、FFmpeg 9.0.2、1920×1080、硬件 AV1。运行真实本机 HTTP 通道、原生帧接入、生产共享控制器、生产 P2P 发送器、真实 RTP 编解码；仅将 DXGI 输入换成合成图像。没有改写统计或用低分辨率通过测试。

三分钟内每 30 秒在静态与运动之间切换，60–120 秒另开测试标签页，随后返回原页。下表按一秒累计计数差分统计，排除最初 5 秒连接启动；静态区间不作为“新运动画面”证据。

| 指标 | 整体 | 运动区间 | 第二测试页激活期间的运动区间 |
| --- | ---: | ---: | ---: |
| 输入 fps | 59.971 | 59.989 | 59.994 |
| 编码 fps | 59.966 | 59.973 | 59.945 |
| 解码 fps | 59.959 | 60.548 | 60.595 |
| 编码 fps 第 5 百分位 | 59.011 | 59.032 | 59.084 |
| 解码 fps 第 5 百分位 | 57.999 | 58.979 | 58.955 |
| 输出 | 1920×1080 | 1920×1080 | 1920×1080 |
| 接收丢包增量 | 0 | 0 | 0 |

解码瞬时值可超过 60，因为抖动缓冲会释放积压帧，不代表生成了额外内容。硬切换附近的解码瞬时值仍有下降与随后追赶，切换样本第 5 百分位约 47.4fps，最大发送队列平均等待约 156.6ms。因此这组数据证明持续运动和线程调度已显著改善，不能证明硬切换时每一秒都严格为 60fps。

运动阶段实际发送平均约 17.22Mbps。已检查一张实际解码的 1920×1080 测试帧；它可以验证图案和细节的输出尺寸，不能替代用户复杂网页的主观画质验收。测试只对小块区域计算变化次数，区域可保持静止，因此该计数不被当成整帧唯一性证明。源侧另外的合成测试验证了 60 个选中运动样本具有 60 个不同完整图像哈希。

原始记录：[三分钟采样](assets/native-pipeline-180s-2026-11-07.json)、[统计汇总](assets/native-pipeline-180s-2026-11-07.summary.json)与[实际解码测试帧](assets/native-pipeline-decoded-2026-11-07.png)。性能脚本位于 `apps/native-capture/diagnostics/browser-pipeline.mjs`，默认只产生测试图像，从不调用桌面选择器。真实桌面的完全静止时可能没有新采集帧，不能直接套用合成源持续采样的结果。

补充的[无新采集帧测试](assets/native-pipeline-idle-2026-11-07.json)只输入一帧，然后停供至 35 秒，再恢复运动。30 秒时 `receivedFrames` 和 `submittedFrames` 仍为 1，保活独立计数，没有把静止补成 60fps。恢复后 45 秒以后的平均输入／编码／解码分别为 59.998／59.998／59.935fps，保持 1080p、无页面或观察器错误。保活最多 1Hz，用于媒体连接与首帧可用性；真实 DXGI 恢复行为仍待实际场景验收。

## 运行与资源约束

本机服务只绑定随机 loopback 端口，要求精确 Origin 和随机能力令牌。能力从 URL fragment 接收后清除；HTTP 流不混入控制文本。服务验证单显示器来源、帧格式、尺寸、包长度和时间戳；异常、取消或页面关闭都会停止其拥有的 FFmpeg 进程。

浏览器选择器的原视频轨道作为不发布的低频权限哨兵保留，浏览器“停止共享”仍能终止原生采集。停止、离会和撤销不等待网络请求才停止本地画面；晚到的授权和来源会清理，重新共享不会被旧授权释放误伤。

源采样数、内容变化数、实际提交帧与低频协议刷新分别统计；静止保活不能算作真实运动 60fps。[Cloudflare 的媒体轨道无媒体包超时为 30 秒](https://developers.cloudflare.com/realtime/sfu/platform/limits/)，1Hz 保活避免原生静止来源被回收，同时保持原有断线／解码停滞恢复逻辑。未引入新的 P2P 控制通道或放宽旧观看者的停滞判断，避免兼容性分叉。
